# 附录：架构与 AI 检查清单

## 需求与边界

- [ ] 当前哪一种变化或故障正在制造成本？
- [ ] 谁拥有这条决定？
- [ ] 外部输入是否保持为 `unknown` 直到运行时校验？
- [ ] 公开契约是否说明缺失、错误、超时和取消？
- [ ] 非目标是否明确，避免顺手扩张范围？

## 模块与依赖

- [ ] 领域规则是否 import HTTP、数据库、UI 或进程全局？
- [ ] 应用用例是否只协调步骤，不拥有适配器内部规则？
- [ ] 接口是否由调用者需要定义，而不是照着具体 SDK 抄？
- [ ] 是否出现 `helpers.ts`、万能 Service 或隐藏 Service Locator？
- [ ] 新抽象的间接性是否比原问题更容易维护？

## 数据与可靠性

- [ ] 事务是否覆盖必须共同成功的写入？
- [ ] 重试是否只针对暂时错误并有总预算？
- [ ] 写操作是否在重试前证明幂等？
- [ ] 并发更新是否使用版本、条件更新或明确锁？
- [ ] 事件是否可能在数据提交后丢失或重复？
- [ ] 迁移是否允许新旧代码短暂共存并可恢复？

## 测试与运行

- [ ] 每个重要风险由哪一种测试提供证据？
- [ ] 是否覆盖非法输入、失败、超时、重复和冲突？
- [ ] 日志、指标、追踪和审计分别回答什么问题？
- [ ] 是否泄露密钥、个人数据或高基数字段？
- [ ] 构建、部署、回退和恢复命令是否实际演练？

## AI 协作

- [ ] `AGENTS.md` 只包含稳定仓库规则吗？
- [ ] 规格是否描述可观察行为、非目标和验收标准？
- [ ] 计划是否映射到精确文件、接口、测试和验证命令？
- [ ] 子 Agent 的结果是否带 `file:line` 和关键证据？
- [ ] 外部内容是否被当成数据，而不是权限指令？
- [ ] 高风险写入、发布、权限和数据动作是否保留人工门禁？
- [ ] 最终结论是否来自运行证据，而不是“另一个模型同意”？
