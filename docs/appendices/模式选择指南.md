# 附录：模式选择指南

先写出当前修改或测试困难，再查这张表。若“当前信号”不存在，默认保持直接方案。

| 当前信号 | 可考虑 | 先尝试的更小方案 | 主要代价 |
| --- | --- | --- | --- |
| 多种算法持续增加并修改稳定流程 | Strategy | 函数参数或小 `switch` | 行为由接线决定 |
| 外部 SDK 接口与内部需要不匹配 | Adapter | 局部翻译函数 | 多一层错误/数据映射 |
| 复杂子系统暴露太多步骤 | Facade | 有业务名的协调函数 | 可能变万能服务 |
| 需要在同一接口上叠加日志/缓存 | Decorator | 在真正拥有者处直接调用 | 顺序和失败语义复杂 |
| 创建实现的选择散落且不一致 | Factory | 单个创建函数 | 创建逻辑被隐藏 |
| 构造结果有很多可选步骤与约束 | Builder | 类型明确的 options 对象 | 无效中间状态 |
| 一次意图需要排队、记录或重放 | Command | 普通输入对象 | 分发链变间接 |
| 状态判断散落且非法迁移增多 | State / state machine | 联合类型 + 集中函数 | 状态版本与迁移维护 |
| 多个独立接收者需要知道变化 | Observer / event | 明确直接调用 | 调用链、顺序和失败不明显 |
| 应用核心被数据库/框架定义 | DIP + Port | 窄函数参数 | 抽象和组合根成本 |
| 多种持久化实现需共同契约 | Repository | 单个保存函数 | 可能掩盖查询/事务差异 |

## 快速停止条件

出现下面任一情况时，先不要引入模式：

- 说不出当前哪种变化正在制造成本；
- 只有一个稳定实现且真实测试可以直接使用；
- 新模式只是把一个 `if` 变成五个文件；
- 抽象名称比它隔离的业务知识更难解释；
- 失败、超时和生命周期在新接口中反而更模糊。
