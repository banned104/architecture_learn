# Node.js + TypeScript 软件架构自学教材设计

- 状态：已确认，开始实施
- 日期：2026-08-23
- 目标读者：已有 React/TypeScript 接触经验，希望系统学习软件架构的初级工程师

## 目标

这套教材不以背诵 SOLID、GoF 模式或架构名词为目标。它要帮助读者面对真实需求时，能够识别变化、划分职责、控制依赖、设计边界，并验证 AI 生成的代码有没有破坏这些边界。

## 主技术路线

- 主语言：TypeScript
- 主要运行时：Node.js
- 后端案例：任务管理 API
- 前端扩展：React
- 示例工程测试：统一使用 Vitest；Node.js 内置测试作为延伸阅读
- 后续持久化：SQLite，再讨论 PostgreSQL
- Python 不进入主线
- C++、Qt、QML、OpenGL 仅在有助于迁移理解时作为对照

## 教学方法

每章采用固定顺序：

1. 提出一个实际问题。
2. 用 5 至 25 行代码让问题落地。
3. 先用人话解释现象。
4. 在同一段引入专业术语并就地注解。
5. 解释一个最小改进，而不是立刻展示完整企业架构。
6. 说明收益、代价以及什么时候不需要这样设计。
7. 用复述题检查是否真正理解。
8. 最后再给图示、扩展阅读或更完整代码。

## 首个里程碑范围（已完成）

第一阶段只交付学习入口、写作规范和第一章，不搭建 Docusaurus，不实现数据库，不引入完整框架工程。第一章围绕一个故意写在一起的任务创建函数，讲清以下关系：

```text
需求变化
→ 变化原因
→ 职责
→ 依赖
→ 模块边界
→ 可测试性
```

## 第二个里程碑范围

第二章继续使用任务创建案例，讲清职责、依赖、依赖方向、耦合和内聚之间的关系。它必须证明：把代码移到不同文件不等于建立了边界，真正重要的是每个模块知道什么、依赖什么，以及变化会沿哪个方向传播。

第二章只增加输入形状校验和窄的持久化函数，不引入完整 Repository 接口、依赖注入容器或框架目录模板。

## 贯穿案例的演进顺序

任务管理 API 会逐步经历：

1. 所有逻辑写在一个处理函数里。
2. 分离输入校验与业务规则。
3. 分离 HTTP、应用用例和持久化。
4. 用测试说明边界为什么存在。
5. 引入 Repository、Adapter 与依赖倒置。
6. 加入 SQLite、错误模型、日志和配置。
7. 通过 React 客户端观察前后端契约边界。

每一步只在当前复杂度确实产生问题后才引入新抽象。

## 非目标

- 不一次性讲完 GoF 23 种模式。
- 不从 Clean Architecture 或 DDD 的完整目录模板开始。
- 不使用微服务、消息队列、缓存、登录或云部署增加首阶段复杂度。
- 不把代码文件数量当成架构质量指标。
- 不让 AI 直接生成最终答案而跳过问题分析与验证。

## 验收标准

- README 能说明学习目标、技术路线、阅读顺序与当前进度。
- AUTHORING_GUIDE 固化正文结构和术语规则。
- 第一章完整包含问题、短代码、人话解释、术语、改进、边界、练习和总结。
- 第一章明确区分“能运行”和“容易修改”。
- Python 不出现在主线示例中。
- 文档不假设读者已经理解耦合、内聚、职责或依赖倒置。
