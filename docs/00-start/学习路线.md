# 学习路线

## 先明确我们不怎样学习

我们不从下面这张清单开始背诵：

```text
SOLID
GoF 23 种模式
MVC / MVVM
Clean Architecture
DDD
微服务
```

这些名称会在课程里出现，但它们是对问题和解法的总结。没有先看见问题时，记住名称很容易产生一种错觉：好像知道模式名称，就已经会设计系统。

课程采用一条逐渐扩大的主线：

```text
一个函数
→ 一个模块
→ 一个 HTTP API
→ 数据库和外部依赖
→ 前后端协作
→ 可以部署和排障的应用
```

## 阶段一：变化、职责和边界

先学会观察代码为什么难改。

主要问题：

- 什么变化会迫使这段代码修改？
- 一段代码是否同时服务多个变化原因？
- 修改影响为什么会传播到无关模块？
- 边界怎样阻止影响继续传播？

实践产物：

- 一张变化原因清单；
- 一次小型函数重构；
- 一段不过度设计的理由。

## 阶段二：从函数走向模块

在任务管理 API 中加入 HTTP 输入、业务规则和保存操作。观察它们为什么不应该长期由同一个函数负责。

主要概念：

- 高内聚、低耦合；
- 依赖方向；
- 输入校验和业务规则的区别；
- 纯函数与副作用；
- 单元测试和集成测试的边界。

实践产物：

- 模块职责表；
- 依赖图；
- 第一组自动化测试。

## 阶段三：原则和常用模式

只有当案例中已经出现扩展困难时，才引入 SOLID 和设计模式。

重点内容：

- SRP、OCP、LSP、ISP、DIP；
- KISS、DRY、YAGNI；
- Strategy、Adapter、Repository、Factory、Observer、Command 和 State；
- Singleton 为什么经常制造共享状态和测试问题。

实践产物：

- 一次重构前后对比；
- 一份模式选择说明；
- 一份“为什么这次不使用某模式”的说明。

## 阶段四：应用架构

任务管理 API 加入数据库、错误模型、日志和配置，React 客户端开始调用它。

重点内容：

- HTTP 层、应用用例、领域规则和基础设施；
- Repository 与 Adapter；
- 分层架构、六边形架构和 Clean Architecture 的共同点与区别；
- React 状态所有权、ViewModel 思想、Flux 与 Redux；
- API 契约和运行时校验。

实践产物：

- 系统框图和数据流图；
- 一个 ADR；
- API 契约与错误表。

## 阶段五：工程质量

架构不仅是目录和类，还包括系统失败时能否理解和恢复。

重点内容：

- 单元、集成和端到端测试；
- 超时、重试、幂等和补偿；
- 日志、指标、追踪和审计；
- 数据库事务、索引和迁移；
- 配置、密钥、构建、部署和回滚。

实践产物：

- 测试策略；
- 故障场景表；
- 从零启动文档；
- 一次故障复盘。

## 阶段六：AI 时代的架构工作

最后讨论怎样让 AI 在明确边界中工作，而不是把大量代码生成当作进度。

重点内容：

- 规格、计划、实现、测试、评审和修复的闭环；
- 项目地图和上下文预算；
- AI 生成代码的架构漂移；
- 如何审查依赖、错误路径、测试和长期维护成本；
- 怎样保存 ADR、验收标准和 Agent 交接记录。

实践产物：

- 功能规格；
- 实施计划；
- 代码评审清单；
- Agent 交接记录；
- 对 AI 生成方案的独立审查。

## 建议节奏

不要按日历强行规定八周完成。每个阶段的完成条件是产物能被解释和验证，而不是文章读完了。

一个阶段结束时，至少应该能够：

1. 不看原文，用自己的话解释核心问题；
2. 在陌生代码中识别相同现象；
3. 写出一个最小改进；
4. 说明改进的成本和不适用场景；
5. 用测试或其他证据证明改进没有破坏行为。
